# プラグインを作る

[English](writing-a-plugin.md) · 日本語

Amenbo のプラグインは、**ただの実行ファイル**です。言語は問いません。Amenbo が子プロセスとして起動し、
標準入力に JSON を渡し、標準出力・標準エラー・終了コードで受け取ります。

この文書は、その規約を作者向けにまとめたものです。Amenbo 本体が入口で強制している規則そのもので、
`amenbo plugin validate` が検査するのも同じ規則です。

> プラグインは Amenbo 2.0.0 から使えます。手元で `amenbo plugin --help` が応えるか確かめてください。

## 2つの面 — フックとコマンド

プラグインは2つの面を持ちます。片方だけでもかまいません。

| 面 | 誰が起動するか | 戻り値 | 失敗したら |
| --- | --- | --- | --- |
| **観測フック** | Amenbo（イベント発生時に自動・非同期） | 使わない | 警告だけ。Amenbo 本体の処理には影響せず、その1件は捨てられます（「配送の約束」） |
| **コマンド** | 人や AI が `amenbo plugin run <name> …` で明示的に | **使う**（標準出力がそのまま戻り値） | 呼び出し失敗として返ります |

フックは**書き込みが確定した後**に走る観測者です。Amenbo の状態を書き換えることも、操作を差し止める
こともできません。実際に何かを「やる」のはコマンドの側です。

## 受け取るもの

### 観測フックの標準入力

イベントが起きると、その JSON が標準入力に流れます。

```json
{
  "v": 1,
  "event": "task.status_changed",
  "id": 42,
  "actor": "ai",
  "at": "2026-07-22T09:00:00Z",
  "new": "in_progress",
  "config": { "base": "main" }
}
```

| フィールド | 意味 |
| --- | --- |
| `v` | ペイロード規約のバージョン。今は `1` |
| `event` | イベント名。下の表のいずれか |
| `id` | 対象レコードの番号（会話で使うあの番号） |
| `actor` | 書き込みを駆動したのが `human` か `ai` か |
| `at` | 発生時刻（`2026-07-22T09:00:00Z` 形式） |
| `new` | 変更後の状態。イベント名だけでは状態が言えないものにだけ付きます |
| `record` | 消えたレコードそのもの。削除のイベントにだけ付きます |
| `parent` | コメントが付いているタスクの番号。`comment.added` と `comment.removed` に載ります |
| `config` | このプラグイン自身の設定のうち、秘密でないもの。未設定ならキーごとありません |

v1 のイベントは11個です。

| イベント | `new` | 何が起きたか |
| --- | --- | --- |
| `task.created` | — | タスクが作られた |
| `task.status_changed` | 新しい状態 | タスクの状態が変わった（終端化を除く） |
| `task.done` | — | タスクが完了した |
| `task.rejected` | — | タスクが却下された（完了と対になる、もう一方の終端） |
| `task.assigned` | 新しい担当 | タスクの担当が変わった |
| `task.moved` | 移動先のスラグ | タスクが別プロジェクトへ移った |
| `task.deleted` | — | タスクが削除された |
| `decision.accepted` | — | 決定記録が採択された |
| `decision.rejected` | — | 決定記録が却下された |
| `comment.added` | — | コメントが付いた（`id` はコメントの番号・`parent` はそのタスク） |
| `comment.removed` | — | コメントが取り消された（`id` はコメントの番号・`parent` はそのタスク） |

変更**前**の値は渡りません。生きているレコードは番号から読み返せるので、v1 が載せるのは新しい状態だけです。
例外は削除で、読み返す先がもう無いぶん、消えたレコードの姿が `record` に載ります。
もう1つの例外はコメントです。コメントはタスクのタイムラインの一部として読むもので、自分の番号からは読めないので、
どちらのコメントイベントも、そのタスクを `parent` で名乗ります。

`v` が上がるのは、既存フィールドの意味が変わるときだけです。フィールドの追加では上がらないので、
**知らないキーは黙って読み飛ばす**書き方にしてください。

### コマンドの標準入力と引数

コマンドとして呼ばれたときは、イベントが起きていないので最小の文書だけが流れます。

```json
{ "v": 1, "config": { "base": "main" } }
```

`amenbo plugin run worktree start 123` の `start 123` は、**そのまま argv** に渡ります。Amenbo は
解釈も書き換えもしません。意味を決めるのはプラグインの側です。

## 返すもの

3つの面で答えます。これは `devtool` が実地で使っていた形をそのまま規約にしたものです。

- **標準出力＝機械が読む戻り値**。呼び出し元（AI やシェル）へ渡ります。
- **標準エラー＝人が読む診断**。要約・エラー・補足。戻り値ではありません。
- **終了コード＝成否**。

面によって扱いが違います。

| 面 | 標準出力 | 規約違反・失敗のとき |
| --- | --- | --- |
| コマンド | 終了コード0なら、そのまま呼び出し元の標準出力へ | 非0やシグナル死なら**戻り値は捨てられ**、失敗が返ります |
| 観測フック | 戻り値としては使われません | 警告のみ。本流に影響しません |

シェルに戻り値を渡す典型は、`cd` する先を1行返す形です。Amenbo はその1行をそのまま素通しし、方言を判定しません。
つまり、その一行が通らなければならないのは呼び出し元のシェルであって、プラグイン側のシェルではありません。

```sh
eval "$(amenbo plugin run worktree start 123)"   # POSIX シェル
```

```powershell
iex (amenbo plugin run worktree start 123)       # PowerShell
```

この形を採るなら、**POSIX シェルと PowerShell の両方でそのまま通る一行**に収め、プラグインの README に両方の起動を
書いてください。`cd '<パス>'` のような一行はどちらでも通ります。分かれるのは引用の逃がし方で、その両立は作者が負う
条件です——Amenbo は呼び出し元のシェルを推測する層を持たず、その一行がどの方言かを知っているのは作者だけだからです。
これを満たせば、`os` に `windows` を含められるかどうかは、実装ではなく起動の書き方だけで決まります。

### 時間の上限

| 面 | 上限 | 超えたら |
| --- | --- | --- |
| 観測フック | なし | 終わるまで待ちます |
| 助言を返すフック（`reply: true`） | 2秒 | 助言なしで先へ進みます。コマンドは止まりません |

観測フックを急かす理由はありません。その後ろに並んでいるのは自分のキューの残りだけで、Amenbo 本体は
とっくに先へ進んでいます。むしろ作業の途中で kill されるほうが困ります——外の世界に半端な結果が残るからです。

`reply: true` を宣言したフックだけは**同期で**走り、その**標準エラー**が呼び出し元へ助言として返ります。
CLI の面でしか成立しません（GUI には受け取って読む相手がいないためです）。

## 配送の約束

フックの配送は2層です。イベントは**起きたことの記録**に積まれ、購読しているプラグインごとの**キュー**へ
振り分けられ、そのキューを**走行役**が頭から1件ずつ処理します。走行役はプラグイン1つにつき1本で、常駐は
しません——Amenbo が動いたときに起動し、自分のキューが空になったら終わります。

この形が何を約束し、何を約束しないかは、プラグインの書き方を左右します。

- **同じイベントが2回届くことがあります。** 処理し終えた直後、その1件をキューから外す前に走行役が落ちると、
  次の走行役が同じ1件をやり直します。プラグインが向こう側で何をしたかは Amenbo からは見えないので、これは
  防げません。**2回目は何もしないように作ってください**——さもないと、同じ投稿が2回出ます。
- **失敗した1件は捨てられます。** Amenbo は実行ログに残すだけで、やり直しません。やり直すかどうかはプラグインの
  側で決めてください。Amenbo が半端な再試行を持つと、プラグイン側の再試行と重なり、結局何回投げられるのかが
  誰にも分からなくなります。
- **1件の失敗で走行は止まりません。** 次の1件へ進みます。1つの失敗が後ろ全部を詰まらせることはありません。
- **順序は同じプラグインの中だけです。** 自分のキューには積まれた順に届きます。**プラグインをまたぐ順序は
  約束しません**（キューが別なので）。同じプラグインの中も原則そうなるという話で、保証ではありません——
  スリープからの復帰や時刻の変更で「走行役はもう居ない」と誤って判定されると、まれに2本並びます。
  時間がかかること自体は関係ありません（走っている間、走行役は生きていると言い続けます）。
  順序が崩れたときの害は、上の二重配達だけです。
- **無効にしている間は届きません。** `amenbo plugin disable` は、そのとき残っていたキューをその場で捨てます。
  再有効化は**今から**始まり、止めていた間の出来事は流れてきません。作成や更新なら現在の状態を読み直せば
  追いつけますが、削除だけは追いつけません。それが困るなら、無効にせず、有効なまま何もしないプラグインとして
  書いてください。
- **即時性は保証しません。** 走行役が途中で殺されたら、残りは次に誰かが Amenbo を触るまで処理されません。
  常駐を持たない代わりに払うものです。

なお、Amenbo に「処理済み」を返す口はありません。**プロセスが返ってきたことが返事**で、成功でも失敗でも
その1件はキューから外れます。作者が実装するものは何もありません。

### 後ろに何件残っているか

起動は1件につき1回なので、プラグインからは自分のキューが見えません。プロジェクトを1つ消せば、そこに何十件も
積まれます。残りの件数は走行役が渡します。

| | |
| --- | --- |
| `AMENBO_PLUGIN_REACH_QUEUE_REMAINING` | **この1件のあとに**まだ積まれている件数。**この起動が発火したプロジェクトのぶん**だけ |

**数える範囲は、見える範囲と同じです**——名前の `REACH` はそれを指しています。下の `AMENBO_PLUGIN_REACH` が
指すプロジェクト、それ1つぶんです。2つのプロジェクトで有効にしていれば、起動はそれぞれのプロジェクトの数を
持って来て、片方の数はもう片方について何も言いません。どのプロジェクトにも属さないレコードの出来事は、
それでひとまとまりとして数えます。数は必ず入ります。

数は `0` まで減るだけで、処理中に増えることはありません。同じプロジェクトに5件積まれていれば `4`・`3`・`2`・
`1`・`0` の順に渡ります。処理している間に積まれた分はその数には入らず、続けて新しい数として届きます。

つまり、まとめ送りはプラグイン側で簡単に作れます——渡された分を**プロジェクトごとに**溜めておき、`0` を見たら
そのプロジェクトのぶんを送る、それだけです。別のプロジェクトで溜めている分はまだ出番ではありません。そちらは
そちらの起動が数で教えてくれます。

**`0` は「この起動の時点で自分のプロジェクトのキューが空」であって、「もう来ない」の約束ではありません。**
直後に書き込みがあれば、それは普通に配られます。`0` で送ったあとにもう1通続くことはありますが、それは1通が
2通になるだけで、届かないことにはなりません。Amenbo は配送を遅らせません——積まれた順に、間を空けずに配ります。

## 設定と秘密

設定項目は manifest で宣言します。値を入れるのは利用者で、渡すのは Amenbo です。
**プラグインが自前で秘密ファイルを読むことはありません。**

| 宣言 | 保存先 | プラグインへの渡り方 |
| --- | --- | --- |
| `secret: true` | ストア（そのプロジェクトの行）。backup には入り、export では落ちます | 環境変数 `AMENBO_CONFIG_<KEY>` |
| `secret` なし | ストア（そのプロジェクトの行） | 標準入力の `config` オブジェクト |

環境変数名はキーから機械的に決まります。大文字にして、英数字でない文字を `_` に置き換えるだけです
（`webhook_url` → `AMENBO_CONFIG_WEBHOOK_URL`）。

**設定はプロジェクトのもので、値は1つです。** プラグインの有効化がプロジェクト単位なので、設定もプロジェクト単位で
答えます。2つのプロジェクトで有効にすれば設定も2組あり、実行時に渡るのは**そのイベントが起きたプロジェクトの値**です。
その下に端末共通の既定はありません。

値が未設定の項目は、環境変数も `config` のキーも作られません。`required: true` を付けた項目は、
値が入るまでそのプラグインを有効化できません（Amenbo が見るのは**値があるか**だけで、妥当かどうかは
プラグインの側の判断です）。

渡るのは**そのプラグイン自身の設定だけ**です。他のプラグインの設定は見えません。

### 欄の種類

何も書かなければ、欄は1行のテキストです。答えが最初から決まっているなら、候補を宣言してしまえば、利用者は
綴りを書かずに選ぶだけになります。

| `type` | 画面に出るもの | プラグインが受け取るもの |
| --- | --- | --- |
| 無し（既定） | 1行の入力欄 | 入力された文字列 |
| 無し ＋ `secret: true` | 1行の入力欄（伏せ字） | 入力された文字列（環境変数で） |
| `multi` | 候補ごとのチェックボックス | 選ばれた値を `,` で連結した文字列 |

```yaml
config:
  - key: events
    label: 通知するイベント
    type: multi
    default: task.done                  # 利用者が答えるまで効く値
    options:
      - value: task.done                # プラグインが受け取る値
        label: 完了した                  # 利用者が読む文字列
      - value: task.rejected
        label: 見送った
```

`default` はテキストの欄にも書けます。「未設定のあいだ効く値」というだけのものです。`default` を持つ欄は
未設定でも答えが決まるので、`required` の指定に関わらず有効化を塞ぎません。

候補の `value` に `,` は使えません（連結に使うため）。`none` も使えません（予約語・下記）。値は互いに
重複してはならず、`default` は自分が出している候補でなければなりません。破っている manifest は validator が
弾くので、出す前に分かります。

**`multi` の欄は3つの状態を持ちますが、プラグインに渡るのは答えだけです:**

| 利用者が | プラグインが受け取るもの |
| --- | --- |
| まだ答えていない | `default` の値 |
| いくつか選んだ | その値を `,` で連結したもの |
| 1つも選ばないと決めた | 空（選ばれた値なし・`default` は効きません） |

最後の行のために `none` が予約されています。「1つも選ばない」という答えを「まだ答えていない」と区別して
保存するための語で、Amenbo が解決してから渡すので、プラグインが `none` を受け取ることはありません。
候補の値としても使えません。

### ラベル1行に収まらないことを書く

`label` は1行です。何のための値なのか、何を書けばいいのかを添えたい欄には、それを持つキーが2つあります。
もう1つは「この値は利用者が打つものではない」という宣言です。

```yaml
config:
  - key: webhook_url
    label: Webhook URL
    help: |
      Slack アプリの Incoming Webhooks から作ります。
      チャンネル1つにつき1本です。
    placeholder: https://hooks.slack.com/services/T000/B000
    secret: true
  - key: worker_url
    label: Worker URL
    help: setup が書き込みます。打つものはありません。
    readonly: true
```

| キー | 何を書くか | 上限 |
| --- | --- | --- |
| `help` | その欄が何のためのものか。入力欄の下に出ます。改行は文字として通ります | 1言語につき UTF-8 で 1KB |
| `placeholder` | 入力例。欄が空のあいだ、中に薄く出ます | 1言語につき 80 バイト |
| `readonly` | 値を書くのはプラグイン自身で、利用者ではない | — |

**どちらの文も平文で、平文のまま描かれます。** Markdown もリンクも描きません。ここは利用者が秘密を打ち込む
画面で、作者が選んだ飛び先を出す場所ではないからです。制御文字も validator が弾きます（`help` は本文なので
改行だけは通ります）——`plugin config get` はこれを端末に出すので、エスケープ列が混ざれば Amenbo が書いた行を
上書きできてしまいます。2つとも設定スキーマ全体のバイト上限にも算入されるので、欄の多いフォームはその分を
ここで使うことになります。

**`placeholder` は `default` ではありません。** `default` はプラグインが実際に受け取る値なので、そこに書いた
入力例は、欄に触れずに有効化した利用者が本当に送る先になります。ここに書いた例は、読まれるだけです。

**`readonly` が縛るのは画面で、書き込みではありません。** フォームは入力欄も消去ボタンも出さずに値だけ見せ、
`amenbo plugin config set` はこれまでどおり書けます。プラグイン自身の値が届く道がそこだからです（値を作る
`setup` が、同じコマンドで書き戻します）。「生成される値とは何か」から2つの規則が出て、validator がどちらも
持っています——`default` は書けません（誰かが生成する前から答えがある値は、生成された値ではありません）。
`type: multi` にも書けません（候補を差し出す相手の利用者がいません）。`required` とは直交していて、両方書けば
`setup` が走るまで有効化は閉じたままになります。

**どちらの文も AI には届きません。** 出るのは人が読む面だけで——フォームは両方を描き、`plugin config get` は
`help` と、どの欄が読み取り専用かを出します——`amenbo agent --json` には載りません。作者の散文は、AI が読む面に
着けば指示として効いてしまうからです。

### 値が使えるかどうかを言う

`required` が見るのは「欄に何か入っているか」だけです。入っているものが実在する webhook なのか、user と
噛み合うパスワードなのか、2つの欄が矛盾していないか——それを言えるのは作者だけです。その判断をする呼び出しを
1本だけ名指しできます。

```yaml
settings:
  check: config check          # 自分のコマンド面。`agent.commands` に書くのと同じ形
```

走るのは、答えがまだ効く2つの場面です——**有効化のとき**と、**有効なあいだの保存のあと**。結果は標準出力に
書きます。

```json
{ "v": 1, "ok": false, "fields": { "smtp_password": "空白が入っています" }, "message": "…" }
```

| キー | 何を言うもの |
| --- | --- |
| `ok` | 値が使えるかどうか。門が開くかはこれだけで決まります |
| `message` | 設定全体についての1文。省略できます |
| `fields` | 設定ごとの1文。設定のキーで引きます。宣言していないキーの行は捨てられ、残りはそのまま効きます |
| `show` | 1文に収まらないもの。結果の下に Amenbo が描く部品の並びです。省略できます（後述） |

**`ok: true` が返らなければ有効化されません。何も言わなかったときも同じです。** 起動しない・非0で終わる・
**2秒**を超える・読めないものを書く——どれも「検査していない」であって「検査して問題なし」ではありません。1文が
**200 バイト**を超えたり制御文字を含んでいたりすると、結果は丸ごと読めない扱いになります。落ちたプラグインの
言い分で有効化してしまうこと——この読み方が防いでいるのはそれです。

**検査が何かを取り消すことはありません。** 保存は止まらず、すでに有効なプラグインが裏で無効に戻ることも
ありません。その場面で結果が効くのは、画面に出る1文としてです。

**作者の文が出るのは設定画面だけです。** `message` と `fields` の各行はそこにだけ描かれます。CLI が出す拒否は
検査が触れた**キーの名前**までで、作者の文は載りません。`amenbo agent --json` に `settings` は出ません。
1行に収まらないものは、実行ログ（`amenbo plugin log <name>`）の標準エラーで読ませてください。

### 利用者が押せるもの

設定画面は、何も書かなければ欄と保存ボタンだけです。`actions` を書くと、すでに答えている呼び出しがボタンに
なって並びます——疎通確認や、結果を `amenbo plugin config set` で書き戻す `setup` などです。

```yaml
settings:
  actions:                              # 4本まで
    - cmd: config test
      label: テスト送信                  # 40 バイトまで。ボタンは短いので
      ask:                              # その1回の実行にだけ渡り、どこにも残りません
        - key: otp
          label: ワンタイムコード
          secret: true
```

ここの `cmd` は `agent.commands` と同じ文法で書く、自分のコマンド面です（サブコマンドと引数であって、
文章ではありません）。同じ呼び出しを起こす `actions` を2つ書けば弾かれます。**押せるのは有効なプラグイン
だけ**で、通る道もほかの実行と同じです——設定値の注入も、読み返しの口も、実行ログも変わりません。門より先に
走るのは有効化のときの検査だけで、それは*有効化*を押した手そのものが許可だからです。

**押した結果を判定するのは終了コードです。** 動いたかどうかはそれが言い、画面に出るのは標準エラーに書いた
1行です。失敗しても何も巻き戻りません。標準出力が読まれるのは1つのことだけ——後述の部品——なので、そこに
`ok` と書いても何も決まりません。検査の2秒も、こちらにはかかりません（何かを立ち上げる `setup` は、
かかるだけかかって構いません）。

`ask` は設定欄の逆で、Amenbo が持たない値です。渡るのは環境変数 `AMENBO_ASK_<KEY>`——キーを大文字にして、
英数字でない文字を `_` に置き換えた名前——で、その1回の実行のあいだだけあり、終われば消えます。

| `ask` に書けるもの | 書けないもの |
| --- | --- |
| `key`・`label`・`secret` | `default`・`required`——読み飛ばさず**弾きます** |

この2つは、設定欄をコピーしてきたときに一緒に付いてくるものです。どちらも「押したあとも生きている値」の
ためのもので、`default` は毎回訊く質問に保存された答えを与えることになり、`required` は有効化の門ですが、
押すことはその門のどちら側でもありません。書けば、起きようのないことを頼んでいる状態になります。

- **1回の押しにつき3つまで。** キーは設定キーと同じ小文字の識別子です。環境変数の名前になる点は変わりません。
- **`config` が保存するキーとは重ねられません。** 1つの名前で「保存される値」と「決して書き残さない値」の
  両方は指せないからです。渡る環境変数の接頭辞が別なのも同じ理由です。
- **`secret` が決めるのは伏せ字かどうかだけです。** 保存先の話はここにはありません。
- **空のまま押されたら、空で渡ります。** 宣言したキーはすべて変数になるので、キーの数だけ読んでください。

**ここまではすべて設定画面の話です。** CLI からはこれまでどおり `amenbo plugin run` で呼べます。こちらは
フォームが渡せない引数を渡せますし、manifest が先に名指ししたものに限られません。

### 1行に収まらないものを画面に出す

検査の `message` も、押した結果に出る標準エラーの1行も、どちらも1文です。セットアップの案内が1文で済むことは
まずありません。`show` はその両方の答えのもう半分で、その呼び出しを起こしたものの下に Amenbo が描く、
部品の並びです。

```json
{ "v": 1, "ok": true, "show": [
  { "text": "スマートフォンのカメラで読み取ってください" },
  { "qr": "https://apps.apple.com/…" }
]}
```

| 部品 | 描かれるもの | 作者が書くもの |
| --- | --- | --- |
| `text` | 説明の1行 | 文字列 |
| `heading` | 長い答えを区切る見出し | 文字列 |
| `note` | 目立たせたい1行（注意書き） | 文字列 |
| `list` | その行を並べたリスト | 文字列の配列 |
| `copy` | コピーボタンの付いた文字列 | 文字列 |
| `qr` | QR コード | QR にする文字列 |
| `link` | ブラウザでページを開くボタン | `url` と `label` |

**作者が書くのは文字列で、描くのは Amenbo です。** ここにマークアップも Markdown も画像もありません。`qr` は
QR にする文字列であって、QR の画像ではありません。この線があるからプラグインは子プロセスのままでいられます
（プラットフォームごとに webview を同梱する必要がありません）。画面の前にいる人が、Amenbo の言葉と他人の言葉を
見分けられるのも同じ線のおかげです。

**同じ語彙は manifest のものでもあります。** `config` は設定欄の並びですが、その間に部品を書けば、作者のコードが
まだ何も走っていないうちから、その位置に描かれます。

```yaml
config:
  - link: { url: "https://myaccount.google.com/apppasswords", label: "Gmail のアプリパスワードを作る" }
  - key: smtp_password
    label: パスワード
    secret: true
```

答えは、まだ何も打っていない人には届きません。呼び出しが `check` しかないプラグインには押すボタンが無く、その
`check` が走るのは有効化のときと、そのあとの保存のときです。行き先の案内がいちばん要るのは、そのどれよりも手前
です。

**`qr` と `link` は公式プラグインだけのものです。** どちらも行き先を持っているからで、QR のほうがなお危ういです
——読むのはスマートフォン、開くのは Amenbo の外で、こちらから止められるものが何もありません。バッジはカタログが
付けるもので作者は付けられないので、ここは機械が判定を誤りようのない線です。第三者にあるのは `copy` で、同じ
文字列を、行く前に行き先を目で読める形で出せます。manifest に書いた場合はどの規則でどこかを名指して弾かれます
（`official_only`）。実行の戻りで返した場合は、その部品だけ落として残りは描かれます。

**上限は、切り詰めずに丸ごと拒否します。** 1つの答えに書ける部品は**10 個まで**、届いた JSON として**4KB まで**
です。どちらかを超えると `show` は丸ごと読まれません。切り詰めれば、Amenbo が編集したものが作者の答えの顔で人の
前に出てしまいます。manifest 側の個数も同じ 10 個で、部品の中の文字列は、スキーマの残りと同じ容量の予算から
引かれます。

もう2つの規則は、どちらの場所でも同じです。**どの文字列にも制御文字は書けません**——ここは利用者が秘密を打ち込む
画面で、`plugin config get` が出す先は端末です。エスケープシーケンス1つで、Amenbo が言ったことの上に書けてしまい
ます。そして **`link` の行き先は `http` か `https` のページだけです**。この機械で何かを起動する scheme は、読み手
が差し出されたボタンではありません。

**2つの実行で違うのは、読めない答えをどう扱うかです。** 検査は fail-closed です——描けない `show` は結果を丸ごと
読めないものにし、それは黙ったのと同じ扱いなので、プラグインは無効のままです。押した結果の標準出力は、もともと
誰も読んでいませんでした。だから答えとして読めないものは、単に「部品なし」です。動いたかどうかは終了コードが
言い、そこに書いた `ok` は読まれません（その語は検査のものです）。

描かれたものが消えるのは、同じボタンをもう一度押したとき、別のボタンを押したとき、そして画面を離れたときです。
設定画面1枚に収まらない量は、標準エラーを読ませる実行ログ（`amenbo plugin log <name>`）の領分です。

**manifest に書いた部品には翻訳がありません。** 翻訳はキーで引きます——欄は `key`、ボタンは `cmd` で——が、部品は
そのどちらも持ちません。書いた言語のまま、掲載が読まれるすべての言語で出ます。静的に書く部品は、それでも通じる
ものに留めて、言語が要る言葉は欄の `label` と `help` に置いてください。

### 出す場面を絞る

全部の欄をいつも描く画面は、Windows の利用者に macOS でしか使えない経路を勧め、誰も選んでいない経路の欄を
スクロールさせます。`when` は、宣言したもののうち、**いま目の前にいる利用者の**画面に出すものを言うためのものです。

```yaml
config:
  - key: transport
    label: 経路
    type: multi
    options:
      - value: icloud
        label: iCloud
        when:
          - { os: [macos] }
      - value: cloudflare
        label: Cloudflare
  - key: worker_url
    label: Worker の URL
    when:
      - { field: transport, has: cloudflare }
settings:
  actions:
    - cmd: worker deploy
      label: Worker を立てる
      when:
        - { field: transport, has: cloudflare }
```

書ける先は3つです——**欄、欄の候補、設定画面のボタン**。条件は2種類しかありません。この Amenbo が動いている
プラットフォームを見る `os` と、別の設定がいま持っている答えを見る `field` ＋ `has` です。複数書いたら
**全部を満たしたときだけ**出ます。並びは `and` で、`or` も `not` もありません。上限は4つです。

`has` が訊くのは「その値が答えの**中にあるか**」であって、「答えの全部がそれか」ではありません。`multi` の欄が
作者の意図どおりに読めるのはそのためです。比べる相手は、プラグインが実際に受け取る値（`default` を解決したあと
の値）なので、誰も触っていない欄も、実際に送られる答えとして読まれます。答えがまったく無い欄は、何とも一致
しません。

**条件が隠すのは箱であって、値ではありません。** Mac で保存した値は、同じストアを Windows で開いてもそのまま
あり、プラグインにもそのまま渡ります。隠すのは画面についての話だからです。隠すことが唯一決めるのは
`required` です——隠れている欄が空でも有効化の門は閉じません。閉じてしまうと、「設定が足りない」と言われた先の
画面に、埋める箱が無いからです。

**判定するのは Amenbo の core で、画面ではありません。** 画面はこのビルドがどのプラットフォームで動いているかを
知らず、core は知っています。だから `amenbo plugin config get` は、画面が描くのと同じ欄について答えます。1つの
manifest について2つが食い違うことはありません。

読めない節は、黙って一度も発火しない規則になる前に、作者の手元で弾かれます（`bad_when`）——どちらの種類も
名指していない節、両方を一度に名指した節、片方だけの節（`has` の無い `field`）、manifest が宣言していない設定を
名指した節、そして自分が書かれている欄を読む節（自分を隠すことしかできません）。`,` を含む `has` も同じです。
`multi` の答えは `,` で連結して保存されるので、`,` を持つ値は決してその中に現れません。

欄の間に描く部品は、まだ `when` を取れません。条件は、欄・候補・ボタンのものです。

## レコードを読み返す

ペイロードが載せているのは id と種類だけで、レコードの中身は入っていません。`id: 42` に対して何かする
なら、まず読むことになります。読み方は、すでに手元にあるもので足ります——**`amenbo` を呼んで
`--json` を付ける**。プラグインは任意の実行ファイルなので、専用のプロトコルもライブラリもありません。

プラグインのプロセスには、自分の居場所からは分からない2つを、Amenbo が起動時に渡しています。

| 環境変数 | 意味 |
| --- | --- |
| `AMENBO_HOME` | 読むストア。実行が起きたストアで、自分のディレクトリから辿れるものではありません |
| `AMENBO_PLUGIN_REACH` | どこまで読めるか。発火したプロジェクトの `AMB-P-<n>` 参照 |

この2つをそのままにしておけば、`amenbo` は何も足さずに正しく答えます。

```sh
#!/bin/sh
id=$(jq -r .id)                       # 標準入力のペイロードがレコードを名指ししている

amenbo task show "$id" --json         # ストアは AMENBO_HOME が決め、範囲は見える範囲が絞る
amenbo task list --filter "done:false" --json
```

**見える範囲は、発火させたスイッチそのものです。** 読めるのは観測しているプロジェクトで、その外は
拒否されます——空の結果ではなく `out_of_reach` と非ゼロ終了です。観測できる範囲が、そのまま読める
範囲です。

自分のプロジェクトディレクトリを探しに行かないでください。プラグインを起動するのは Amenbo であって、
フォルダに立っている人ではありません。足下に `.amenbo` は無いのが普通で、だからこそストアは
探させるのではなく名指しで渡しています。

これは隔離ではありませんし、Amenbo もそう言い張りません。プラグインにはシェルがあるので、檻にはなり
えないからです。信頼の線は、利用者が有効化したという事実の側にあります。この入口があるのは、必要な
中身に**壊れない正規の経路**を用意するためです。

ここで読むのは、フックが名指しした1件です。データを丸ごと端末の外へ運ぶなら、そのための口が別に
あります——[データを外へ運ぶ](carrying-data-outward.ja.md)。

## manifest

配布の単位は manifest 1枚です。公式カタログに載せるなら、このリポジトリに
[`plugins/<name>.yaml`](../plugins/) を1ファイル追加する PR を出します。

### 必須

| フィールド | 意味 |
| --- | --- |
| `name` | カタログでの識別子。ファイル名とも、インストール後のディレクトリ名とも一致します |
| `desc` | 一覧に出る1行説明 |
| `author` | 作者の表示名（これで公式バッジが付くわけではありません） |
| `repo` | ソースリポジトリを `owner/name` で |
| `os` | 動作する OS。`macos` / `windows` / `linux` から1つ以上 |
| `category` | 絞り込み用のラベル（例 `workflow`） |

…に加えて、配布物を次の**どちらか一方**の形で書きます。

- 全 OS で1つのファイル（スクリプトなど）: `url` と `checksum`
- OS ごとに別のビルド: `assets`（キーごとに `url` と `checksum`）

`assets` のキーは `<os>`（その OS の全アーキテクチャ）か、`<os>-<arch>`（`arm64` / `x64`）です。
実行時は `<os>-<arch>` を先に探し、無ければ `<os>` を見ます。

### 任意

| フィールド | 既定 | 意味 |
| --- | --- | --- |
| `title` | なし | 一覧で `name` の代わりに出る表示名。`name` の文法（小文字 ASCII と `-`）では書けない製品名のためのものです。60字まで。訳しません。書かなければ、一覧には `name` が出ます |
| `about` | なし | プラグインの詳細画面に出る長い説明文。Markdown で書きます。書かなければ、その画面には `repo` の README が出ます。書き方と、いくつの言語で書けるかは後述 |
| `official` | `false` | 公式バッジ。カタログのキュレーションが決めるもので、自己申告はできません |
| `payload_v` | `1` | 読むペイロード規約のバージョン |
| `min_amenbo` | なし | 必要な Amenbo の下限バージョン（semver） |
| `config` | なし | 設定画面。受け取る欄（`key` / `label` / `help` / `placeholder` / `secret` / `required` / `readonly` / `type` / `options` / `default` / `when`）と、その間に描く部品（前述） |
| `settings` | なし | その画面が起こす呼び出し。有効化のときに走る `check` と、利用者が押す `actions`。どちらのボタンも自分の `when` で出し分けられます（前述） |
| `events` | なし | フックが反応するイベント。無ければコマンド専用のプラグインです |
| `agent` | なし | AI が「ここでの働き方」を読む場所で、どう動かすかを書くもの。`when` / `commands`。どこまで AI に届くかはバッジ次第です（後述） |

`events` の各項目は、イベント名そのものか、発火する場面を絞ったオブジェクトです。

```yaml
events:
  - task.done                  # CLI でも GUI でも発火し、助言は返さない
  - event: task.status_changed
    faces: [cli]               # cli / gui。空にはできません
    reply: true                # 助言を呼び出し元へ返す。faces: [cli] のときだけ
```

知らないキーは拒否されず読み飛ばされます。新しい Amenbo 向けに書いた manifest が、古い Amenbo で
パースできずに落ちることはありません。

### どの文にも書けないもの

読み手に向けて書く文字列は、**Amenbo の記録番号を引くと弾かれます**——`desc` と `about`、設定欄の
`label`・`help`・`placeholder`、設定画面のボタンの `label` と押したときに訊く欄のラベル、`agent.when` と
各 `does`。引用と見なされるのは `AMB-D-<n>`・`AMB-T-<n>` のように、`AMB-` と種類の1文字と数字が単語として
立っている形で、大文字小文字は問いません。

この番号は、それが振られたストアの中でしか意味を持ちません。作者の文に置かれると、そのストア自身の記録の
ように読めてしまいます——「`AMB-D-<n>` により必須」は、Amenbo が書いていない文に利用者の権威を借りる形です。
実在しない番号でも同じように読めてしまうので、番号は照合しません。**綴りだけが判定のすべて**で、訳文も manifest と
同じ規則で見られます。

`#42` や `T-42` には手を出しません。GitHub や他のトラッカーのもので、Amenbo が取り上げれば、もともと自分の
ものでない参照を横取りすることになるからです。自分のリポジトリの issue 番号は、そのまま書けます。

### 自分が何のためのものかを名乗る

フォルダで働く AI は、`amenbo agent --json` という1つの文書を読んで「ここでの働き方」を知ります。利用者が
入れて有効にしたプラグインも、その文書が答えるべきものの一部なので、あなたのプラグインもそこに名前が出ます。
どう動かすかを書く場所が、省略可の `agent` です。

```yaml
agent:
  when: このプラグインに手を伸ばす局面（1行）
  commands:
    - cmd: <サブコマンドと引数>
      does: それが何をして、何を返すか（1行）
      steps: [<この呼び出しが道具になる、Amenbo 自身の step の ID>]
```

| 項目 | 意味 |
| --- | --- |
| `when` | どういうときに手を伸ばすか。ブロックを書くなら必須です（局面を名乗らないブロックは、読む側に何も渡しません） |
| `commands` | コマンド面が応える呼び出しを1件ずつ。無くてもかまいません |
| `steps` | 呼び出し1件につき、それが Amenbo 自身の運転手順のどこで道具になるか。書かなければ、どこにも紐づきません（後述） |

**書くのは自分のコマンド面だけです。** `amenbo plugin run <プラグイン名> ` の前置は、読み取った名前から
Amenbo が付けます。読む側にはそのまま打てる1行が届きます。作者が丸ごと書くと自分の名前を自分で書くことになり、
この形が避けたいのはまさにそこです。

**観測フックしか持たないプラグインは、`when` だけを名乗れば十分です**（`commands` は書きません）。呼ぶものが
無くても、「どういうときに効いているか」は言う価値があります。

#### その呼び出しが道具になる場所

`amenbo agent --json` の大半は Amenbo 自身の運転手順で、いくつかの run に分かれた step の連なりとして書かれて
います。step にはそれぞれ `id` があります。step は「タスクごとに worktree を切れ」とは言えても、コマンドは
名指しできません——Amenbo のソースにプラグインの名前は1つも現れないからです。だから「切れ」と言われた AI は、
自力であなたのプラグインを見つけるまで手がありません。

その穴を埋めるのが `steps` です。自分の呼び出しが効く step を名指すと、Amenbo がその step に「打つための1行」を
`tools` として掛けます。

```yaml
commands:
  - cmd: start <task-id>
    does: Cuts a worktree for the task outside the repository, and returns the line to cd into it
    steps: [worktree.cut-per-task, worktree.run-the-line]
  - cmd: finish <task-id>
    does: Removes that worktree and its branch, once the work has been merged
    steps: [worktree.fold-it]
```

ID は `<run>.<step>`、2つの名前をドット1つでつないだ形です。

- **run** — バックボーンなら `agentCycle`、そうでなければ cycle のキー（`cycles.worktree` なら `worktree`）
- **step** — その run の中での `id`

どちらも文書そのものから読めます。`amenbo agent --json` には run と、その中の step の `id` が全部出ています。
1つの呼び出しが名指せるのは4つまでです。

**渡るのは打つための1行だけです。** `when` と各 `does` はあなたの欄に残り、読む側はそれをあなたの言葉として
受け取ります。step の本文は Amenbo 自身の運転手順であり、その一語一語に Amenbo が責任を持つからです。
この項目だけが公式プラグインと第三者とで同じ扱いなのも、そこが理由です——`cmd` は文法が決まっているので、
文を乗せたまま向こう側へは渡れません。

**無い step を名指しても、エラーにはなりません。** step は Amenbo と一緒に更新されるのに、あなたの manifest は
入った場所に留まります。名前が変わることも、廃止されることもあります。cycle ごと出てこないこともあります
（git のチェックアウトの外では `worktree` の cycle がまるごと落ちます）。行き先の無い ID は、どこにも
掛からないだけです。ほかのものを道連れにはしません。

#### AI に届くのはどれか

**作者が書いた文が AI に中継されるのは、公式プラグインだけです。** 公式でないプラグインについて、入口に
出るのは次のとおりです。

| | AI に届くか |
| --- | --- |
| `name` と `events` | 届きます。Amenbo が決めた語彙であって、作者の文ではありません |
| 各 `cmd` と、それを掛けた `steps` | 打つための1行として届きます。文法が決まっているので、文は入りません |
| `when`・各 `does`・`desc` | **届きません** |

`desc` は消えるのではなく、宛先が違うだけです。`plugin list` には誰が書いたものでも出ます。あの面を読むのは
人だからです。`when` と `does` は、バッジが無いかぎり今のところ誰にも届きません。

**なぜ中身ではなく作者で線を引くのか。** その文がプラグインの説明なのか、読んでいる AI への指示なのかは、
機械には判定できません。そして、公開されるものを事前に読むレビュアーはいません——カタログは棚であって、
レビューの列ではないからです。公式バッジはカタログのキュレーションが付けるもので、自己申告はできません。
だから、あなたがどちら側かを機械が判定でき、しかも間違えようがない線は、これ1本です。
Amenbo は文を濾過しません。そもそも入る欄を作らない、という安全側を採ります。あとで緩めるのは簡単ですが、
一度届けたものを引っ込めるのは難しいからです。

それでも、ブロックは書いてください。`when` は、書くと決めた時点で必須です。`cmd` はあなたのプラグインを
AI まで運ぶものです。将来この規則が緩んだとき、書いてあるものはそのまま効きます。

もう2つ:

- **中継されるものは、書いた言語のまま通ります。** Amenbo 自身の入口は複数の言語を併せ持ちますが、
  作者の言葉に対する訳は持っていません。
- **載るのは有効なプラグインだけです。** 有効でないものは呼んでも拒否されるので、入口にも出しません。

### 他の言語で書く

あなたが書くもののうち、**人が読む**のは3つです——`desc`、`about`、設定画面の文字（欄やボタンのラベルと、
それに添える `help`・`placeholder`）。この3つは、訳があれば読み手の言語で出ます。ほかは書いた言語のまま
残ります。
`agent.when` と各 `does` を読むのは AI であり、CLI の出力は英語で固定なので、どちらも選ぶ訳を持ちません。

**`about` は Markdown で、YAML のブロックスカラーが中身を運びます。** `desc` が一覧に並ぶ1行なのに対して、
`about` は詳細画面に出る本文です。manifest でも、その訳でも、書き方は変わりません。

```yaml
# plugins/mail.yaml
desc: Report what your AI did by email
about: |
  Every task your AI finishes reaches you as a mail — what it was, and how it ended.

  Bring any SMTP server you already have. For Gmail, an app password is all it takes.
```

決まりは2つあり、manifest 側の1本にも、各言語の訳にも、同じようにかかります。

- **1言語につき UTF-8 で 2048 バイト。** 日本語ならおよそ1000字、英語なら2000字ほどです。README ではなく
  説明文なので、install すると読み手に何が起きるかだけを書き、残りはリポジトリに任せてください。
- **リンクと画像は絶対 `https://` URL だけ。** 相対パスも `http://` も弾かれます。`about` を描くのは
  Amenbo で、中身はカタログが配る文書から来ます。`./README.md` が指す先になるページは、どこにもありません。

訳は **manifest の隣に置くファイル**で、ファイル名が言語を表します。

```
plugins/mail.yaml       # manifest 本体。これは英語
plugins/mail.ja.yaml    # 日本語
plugins/mail.de.yaml    # ドイツ語
```

訳した欄だけ書いてください。書かなかった欄は manifest の値に落ちます。1欄だけ訳したファイルも、そのまま
出して構いません。

```yaml
# plugins/mail.ja.yaml
desc: AI がやったことをメールで報告する
about: |
  AI がタスクを終えるたびに、何をどう終えたかがメールで届きます。

  SMTP サーバーは手持ちのもので構いません。Gmail ならアプリパスワードだけで足ります。
config:
  smtp_host:
    label: SMTP サーバー
    help: Gmail なら smtp.gmail.com です。
    placeholder: smtp.gmail.com
  events:
    label: 何を報告するか
    options:
      task.done: タスクが完了した
settings:
  actions:
    config test:                      # 元の action の `cmd` が見出しになります
      label: テスト送信
      ask:
        otp: ワンタイムコード          # 元の ask の `key` が見出しになります
```

**`config` と `settings.actions` は、ここでは配列ではなく表です。** manifest では画面に並べる順そのままの
配列ですが、訳では欄を `key` で、選択肢を `value` で、ボタンをそれが起こす `cmd` で、押したときに訊く欄を
その `key` で引きます。訳は自分の順番を持ちません。位置で対応づけると、フォームを並べ替えた日に全言語が
いっせいに壊れます。

| 訳せるもの | 訳せないもの |
| --- | --- |
| `desc`・`about` | `name`・`title`・`author`・`repo`・`category` など manifest の残り |
| 設定欄の `label`・`help`・`placeholder` | 設定欄の `key`・`type`・`default`・`readonly`、および選択肢の `value`（プラグインに渡る値そのもの） |
| 選択肢の `label` | `agent.when` と各 `does`（読むのは AI なので英語のまま） |
| ボタンの `label` と、そこで訊く欄の `label` | `settings.check` と action の `cmd`（呼び出しであって読ませる文字列ではないので、訳を書く場所がありません） |

言語は Amenbo 自身が読まれる19言語です: `en`・`ja`・`zh-Hans`・`zh-Hant`・`ko`・`es`・`pt-BR`・`fr`・`de`・
`it`・`ru`・`hi`・`id`・`vi`・`th`・`tr`・`pl`・`nl`・`uk`。

訳は manifest と一緒に、同じコマンドで検査されます。manifest を渡せば、隣にあるものも一緒に読まれます。

```sh
amenbo plugin validate plugins/mail.yaml
```

弾かれるのは4つで、どれもファイルがまだ手元にあるうちに直せるものです——19言語の外の言語コード、manifest に
無い欄、manifest が宣言していない `key`・選択肢の `value`・action の `cmd`、元の欄と同じ文字数上限を
超えた文。黙って無視されるものはありません。打ち間違えた見出しの下に埋もれて、どこにも出ないラベル——この入口が防ぎたいのは
それです。

カタログは、この2つを読まれ方どおりに配ります。`desc` は一覧の隣に置く `catalog.<lang>.json` に入るので、
一覧を見る人は自分の言語1本だけを取ります。`about` と設定欄のラベルは `plugins/<name>.json` の中に全言語
まとめて入ります。この文書を取るのは、そのプラグインを開いた人か install する人だけです。だから詳細画面は
読み手の言語に追随し、設定欄は install したあと通信なしで追随し続けます。まだ誰も開いていない一覧に、
19言語ぶんの長い説明文を積む理由はありません——`about` が詳細側に入るのはそのためです。どちらも作者が
組み立てるものではありません。

## 配布物の形

`url` が指す先は、次のいずれかです。中身は先頭バイトで判別され、拡張子は見ていません。

- **`.tar.gz`** — 中から、**プラグイン名と同じファイル名**の通常ファイルが取り出されます
  （Windows なら `<name>.exe`）。ディレクトリが1段挟まっていてもかまいません。
- **実行ファイルそのもの**
- **`.zip`** — Windows 向けの資産に限ります。他の OS では拒否されます。

取り出されたものは、Amenbo のアプリデータ配下 `plugins/<name>/` に、その名前の実行ファイルと
`manifest.json` として置かれます。**何を実行するかは manifest に書けません**——名前の規約で決まります。

## 署名と検証

install は次の順で、1つでも欠ければ**何も書かずに止まります**。

1. カタログの鍵による **minisign 署名**の検証
2. その OS 向けに宣言された **checksum** の照合

いずれも URL が実際に返したバイト列に対する検証です。

**作者は鍵を持たず、署名もしません。** 署名するのはカタログの CI で、merge のときだけです。署名が意味するのは
「このバイト列はカタログを通った」——レビューされ、ダウンロードされ、ダイジェストが確かめられた——ということで、
作者個人の保証ではありません。

どの鍵で検証するかは、そのプラグインが**どのカタログから来たか**で決まります。公式カタログのものは Amenbo に
同梱された鍵、`amenbo plugin catalog add <url>` で登録されたカタログのものは**そのカタログが公開している鍵**
（登録のときに指紋を見せて pin されたもの）です。鍵を公開していないカタログは、閲覧はできても install は
できません。どのカタログにも載っていない資産は install できません。

pin した鍵は、そのまま守られます。登録したときと違う鍵で署名された資産を、Amenbo は黙って受け入れません
——**鍵が変わった**と告げて止まります。古い同意は新しい鍵には効きません。信頼し直すなら、その配布元を
`amenbo plugin catalog remove <url>` して `add` し直します。その1往復で、新しい指紋がもう一度あなたの前に
出ます。

自分でカタログを建てて配るなら、[カタログを建てる](running-a-catalog.ja.md)にその手順があります。

## install ≠ enable

install はバイナリを置くだけで、何も動かしません。動き出すのは `amenbo plugin enable <name>` の後です。
**有効にすること自体が、任意のコードを走らせる許可**です。

スイッチはプラグインごとに1つ、プロジェクト単位です。プロジェクトごとに答えが決まり、利用者に2つの
スイッチを見せることはありません。

有効化のとき、Amenbo は互換性も確かめます。

- `payload_v` は**一致**が要ります（規約が壊れる変更でしか上がらないので、どちらに違っても話が通じません）
- `min_amenbo` は動作中のバージョンが**下限以上**であること

`required` の項目が空のままなら、有効化は断られます。自分で書いた `check` が `ok: true` を返さないときも同じです。

## 出す前の自己チェック

Amenbo が入口で使うのと同じ検証を、手元で回せます。

```sh
amenbo plugin validate plugins/<name>.yaml
```

見つかった問題をすべて並べて、1つでもあれば非0で終了します。カタログの PR でも、この同じ検証が走ります。

## 動かないときに見る場所

フックは撃ちっぱなしなので、失敗しても呼び出し元には何も出ません。「なぜ何も起きなかったのか」に
答えるのが実行ログです。

```sh
amenbo plugin log          # 全プラグインの直近の実行
amenbo plugin log <name>   # 1つに絞る
```

いつ・どのプラグインが・どのイベントで走り、どう終わったか（終了コードと所要時間）が1行ずつ出ます。
きれいに終わらなかった実行には、そのプラグインが**標準エラー**に書いたものが続きます。診断をそこに
書いておくのは、そのためです。
